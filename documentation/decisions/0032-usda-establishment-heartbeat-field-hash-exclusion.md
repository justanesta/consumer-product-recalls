# 0032 — USDA establishment `latest_mpi_active_date` hash exclusion (upstream heartbeat fields)

- **Status:** Accepted
- **Date:** 2026-05-13
- **Supersedes:** —
- **Superseded by:** —
- **Clarifies:** ADR 0007 (extends `hash_exclude_fields` use to a new category — upstream-driven volatile fields, distinct from FDA's RID query artifact and NHTSA's regen-unstable RECORD_ID); ADR 0027 (this ADR adds a third category of bronze re-version wave, complementing the schema-normalization wave that ADR 0027 addressed); ADR 0030 (parallel decision pattern — hash-exclude a field that flips without representing semantic change).

## Context

### What prompted this ADR

The 2026-05-13 routine extract of `usda_establishments` inserted 7,184 of 7,970 fetched records (~90%). Investigation via `scripts/sql/_pipeline/recent_runs.sql` revealed a recurring weekly-ish pattern:

| Date | Extracted | Inserted | Notes |
|---|---|---|---|
| 2026-05-01 | 7,945 | 6,859 | Initial seed (re-versioned against pre-window history) |
| 2026-05-02 | 7,945 | 7,786 | Second wave |
| 2026-05-06 (Tue) | 7,956 | 7,176 | Third wave |
| 2026-05-13 (Tue) | 7,970 | 7,184 | Fourth wave |
| (intervening days) | ~7,956 | 0 | No-op re-fetches |

Between waves, daily re-fetches produce 0 inserts (idempotent). On Mon/Tues — FSIS's documented publishing cadence — ~90% of the corpus re-versions in a single batch.

The `scripts/sql/usda_establishments/bronze/diagnose_rebaseline_column_diffs.sql` fingerprint pinpointed the cause:

```
total_compared = 7170
latest_mpi_active_date_diff = 7170   ← 100% of compared records
everything else            = 0 to 11 ← noise-level real edits
```

The `sample_old_vs_new_diff_columns.sql` companion script confirmed the pattern: across May 1 / May 2 / May 6 / May 13 versions of the same establishment, every other displayed field stayed constant while real edits (e.g., `duns_number` populated for the first time, `phone` corrected) showed up in single-digit counts. FSIS bumps `latest_mpi_active_date` on every directory republish for ~every establishment, regardless of whether anything semantic changed for that record.

### What was already decided

Two prior precedents for `hash_exclude_fields`, both for a different category than this ADR addresses:

- **FDA (ADR 0007, original use case).** The FDA `openFDA` endpoint's `meta.results.skip` position counter (carried as `rid_position`) increments with each pagination request. It's a query artifact — a property of *how we fetched*, not of the record's content. Excluding it from the hash prevents pagination order from versioning bronze.
- **NHTSA (ADR 0030).** RCL.txt's `RECORD_ID` (`source_recall_id`) is regenerated on each TSV rebuild. Same logical row, different RECORD_ID across regens. Also a query/fetch artifact — a property of NHTSA's file-build process, not the underlying recall.

`latest_mpi_active_date` is neither. It's a **substantive field** that FSIS populates from its internal MPI directory state, with semantic meaning ("the most recent date this establishment was confirmed active"). It just happens to update on every directory republish — making it an **upstream-driven heartbeat** rather than a query artifact.

### The architectural question

When should a substantive field — one that *means something* and is populated from real upstream state — be excluded from the bronze content hash?

## Decision

**Exclude `latest_mpi_active_date` from the USDA establishment content hash via `hash_exclude_fields={"latest_mpi_active_date"}` on the establishment `BronzeLoader`.**

The criterion for adding a substantive field to `hash_exclude_fields` is:

> A field that updates on every upstream republish for ~all records, independent of whether the rest of the record changed, such that including it in the hash makes the loader treat ~all rows as re-versioned on every refresh cycle.

This is the **third category** of `hash_exclude_fields` use, alongside the prior two:

| Category | Example | Why excluded |
|---|---|---|
| **Query artifact** | FDA `rid_position` | Property of how we fetched, not the record |
| **Fetch-build artifact** | NHTSA `source_recall_id` (RECORD_ID) | Regenerated by upstream file builder per run |
| **Upstream heartbeat** *(this ADR)* | USDA establishment `latest_mpi_active_date` | Upstream-bumped on every refresh for ~all records, independent of record content |

The field continues to be **stored in bronze** — it's a real piece of FSIS data with downstream utility. It's only removed from the **hash input** so that its movement alone doesn't trigger a re-version. The latest value is still queryable via `select distinct on (source_recall_id) latest_mpi_active_date order by source_recall_id, extraction_timestamp desc`.

### Implementation

```python
# src/extractors/usda_establishment.py
loader = BronzeLoader(
    bronze_table=_establishments_bronze,
    rejected_table=_establishments_rejected,
    identity_fields=("source_recall_id",),
    hash_exclude_fields=frozenset({"latest_mpi_active_date"}),
)
```

One-line change. Mechanism (`hash_exclude_fields`) already exists; this is a new application of an existing pattern.

## Consequences

### Positive

- **Weekly bronze re-version waves shrink from ~7,184 phantom rows to ~5–50 real-edit rows.** Today's wave included 2 records with newly-populated `duns_number` and 1 phone correction — the kind of real edits we want to capture. After this fix, those are the only rows that would land per cycle.
- **`recall_event_history` (Phase 6, ADR 0022) inputs become cleaner.** Edit detection across bronze versions won't be drowned out by heartbeat noise.
- **Storage savings.** ~7k bronze rows × ~52 cycles/year ≈ ~360k phantom-versioned rows/year not written.
- **Establishes precedent for future sources.** When EPA or other future sources land, the criterion in this ADR gives a clear test: "does this field update for ~all records on every refresh independent of content?"

### Negative

- **Loss of per-version `latest_mpi_active_date` history in bronze.** A change to `latest_mpi_active_date` alone (with no other field change) will no longer create a new bronze row. If we later want per-week-history of MPI active dates per establishment, we'd need a separate sidecar table fed from raw landings — or revisit this ADR. **Mitigation:** the field is administrative (an FSIS-side activity timestamp), not a publication date or transaction date; per-version history has no business meaning we've identified. Finding G already documents the field as "administrative, not a publication timestamp."
- **One-way migration of today's bronze.** The 7,184 phantom-versioned rows from 2026-05-13 (and the prior May 1/2/6 waves) remain in bronze. Silver's latest-per-id `distinct on` pattern means downstream is unaffected, but bronze carries the historical noise. Acceptable on dev; no cleanup required.

### Neutral

- The field stays in the Pydantic schema and bronze table. Only the hash computation skips it.
- No silver / staging model changes required — `stg_usda_fsis_establishments.sql` already picks latest-per-id by `extraction_timestamp`, which continues to work.
- The `change_type=schema_rebaseline` mechanism from ADR 0027 is **not** needed here — this is a content-hash criterion change, not a Pydantic-schema change, and the only effect of the change is to *suppress* future re-versions, not produce one.

## Validation

The fix is testable on the next FSIS publishing day:

- **Before:** Mon/Tues republish day produces ~7,000+ inserts on `usda_establishments`.
- **After:** Same Mon/Tues republish day should produce 0–~50 inserts (whatever real edits FSIS shipped that week).

If a post-fix Mon/Tues wave still produces hundreds-to-thousands of inserts, a secondary volatile field exists. Most likely candidate: `grant_date` (though it should be set-once per establishment, not refresh-time — would warrant investigation).

A small residual of ~5–15 bronze inserts per wave is expected and benign — it reflects legitimate upstream byte changes (real edits like `duns_number` population, `phone` corrections, plus FSIS's array-element whitespace flips on `activities` / `dbas` that we observed between May 1 and May 2). Silver staging (`dbt/models/staging/stg_usda_fsis_establishments.sql:49-60`) already normalizes the array-whitespace cases via `jsonb_agg(trim(elem))` per ADR 0027, so silver/gold see no churn from them either way. No follow-up needed for the whitespace observation.
