- [x] **NHTSA bronze dedup lookup is O(corpus), not O(delta): daily `recalls extract nhtsa` runs ~17 min and worsens as bronze grows.** This is the real fix behind the symptom investigated 2026-06-10; the inner-SHA short-circuit shipped the same day (`feature/pre-go-live-validation`) only papers over *no-change* days.
  - **STATUS — FIX BUILT 2026-06-11 (`feature/pre-go-live-validation`).** Conservative **fetch-only** restructure of `BronzeLoader._fetch_existing_hashes` (`src/bronze/loader.py`): batches above the bind-param ceiling (NHTSA's ~241k full dump) now run one set-based **TEMP-table staging JOIN** (`_fetch_existing_hashes_staged`) instead of ~45 chunked IN seq-scans — O(corpus) one pass vs O(corpus × chunks). It is a pure `IN → JOIN` with byte-identical text-canonical comparison, so the dedup *decision* (`filter_new_records`) and `load()` are untouched — correct by construction (chose this over the typed-temp and full-anti-join options, which add risk near the dedup oracle for no net gain; see plan). Uses a `pg_temp` table (no `CREATE`-on-public; `recalls_app` has database `TEMPORARY` via PUBLIC — verified in `verify_recalls_app_grants.sql` §0.6) + `ANALYZE` for the hash-join plan. **Differential equivalence (staged == old chunked loop) PASSED on a prod-clone Neon branch over 50k real identities + absent keys** (`tests/bronze/test_loader_fetch_equivalence.py`).   - **Symptom + empirical proof (from `extraction_runs`).** The 17 min is not "load 1,857 rows" — the incremental path is a full dump that processes all ~241k POST_2010 rows every run and inserts only the delta. The cost is one stage: the existing-hash dedup lookup (`src/bronze/loader.py:242` `_fetch_existing_hashes`). Same-corpus deep-rescans on 2026-06-02 prove the insert is *not* the bottleneck: run 94 inserted **321,425 rows in ~8 min** (seeding near-empty bronze → cheap lookup), while runs 95/96 inserted **0–167 rows in ~21–22 min** (full bronze → expensive lookup). Duration tracks how full bronze is, *inversely* to insert count. Run 323 (2026-06-10, ~241k bronze, 1,857 inserted, ~17 min) sits exactly on that curve.
  - **Root cause.** `_fetch_existing_hashes` fetches the latest hash for **all** ~241k identity keys every run and matches on NHTSA's 11-tuple identity wrapped in `coalesce(cast(col AS text),'')` / `coalesce(to_char(col AT TIME ZONE 'UTC',…),'')` (`loader.py:161`). No index can serve that predicate — the only `nhtsa_recalls_bronze` indexes are `ix_nhtsa_recalls_bronze_id_ts` on `source_recall_id` (which is **excluded** from the dedup identity per ADR 0030) and `ix_nhtsa_recalls_bronze_campno` (1 of 11 cols, also wrapped). So each of ~45 chunks (60k-param ceiling ÷ 11 cols) is a **full seq-scan** that recomputes 11 text expressions per row, hash-groups, and self-joins back to bronze — over the network to small-compute Neon. Cost ≈ `bronze_rows × chunks`; it gets worse every day bronze grows.
  - **The fix = W10/R9** (shipped): conservative **fetch-only** restructure — `BronzeLoader._fetch_existing_hashes_staged` loads incoming identity keys into a `pg_temp` table, `ANALYZE`s it, then runs the same two-stage `GROUP BY max(extraction_timestamp)` JOIN as the chunk path (one bronze pass instead of ~45). The dedup decision (`filter_new_records`) is unchanged — correct by construction. The full anti-join (`INSERT…SELECT…WHERE NOT EXISTS`) was rejected for relocating the dedup decision into SQL (see ADR 0041). Achieved: ~17 min → ~61 s on the real daily run.
  - **Why promote it now.** W10 is currently marked *"Defer (likely won't-do post-W6)"* on the rationale that the W6 short-circuit makes no-change deep-rescans ~5s, so the lookup only burdens *rare* real-change runs. The measurement the plan was "deferring pending" is now in hand (~17 min/run, lookup-dominated). The 2026-06-10 inner-SHA short-circuit is the daily analog of W6 and only covers the quiet days; W10 is what makes the *change* days fast.
  - **Guardrails (from the plan — honored).** Text-canonical normalization preserved exactly via `_identity_text_expr` on both sides of the JOIN. SQLAlchemy chunked multi-row `INSERT`s used (no `psycopg2` COPY). Dedup decision stays in Python (`filter_new_records` unchanged). Full-corpus differential regression test shipped: `tests/bronze/test_loader_fetch_equivalence.py`. `BronzeLoader` dedup oracle untouched — fetch-only restructure. Refs: `documentation/audit/deep_rescan_reliability_audit.md` (Problem 1), ADR 0041, `src/bronze/loader.py:243`.
